Access Management

Restrict menus, models and fields per user from a single screen.

Odoo 19.0.1.1.0 Odoo 19.0 Community License: LGPL-3 CPSS

Technical name: cpss_access_management  ·  Depends on: base, web

Centralises in one application everything a functional administrator needs to restrict what a user may see and do, without writing a line of XML or Python: hide menus, forbid create / edit / delete / duplicate / export / archive on a model, hide the action and print menus, turn any field invisible, read-only, required or link-less, hide buttons, notebook tabs, the chatter, the filters and the group by entries, forbid a given report, and narrow the records a user may reach with a dynamic domain.

Overview

Access rights in Odoo are designed around groups. As soon as two users must share a group but not the same screens, the standard answer is a technical group, a record rule and an inherited view — three artefacts to write, to version and to maintain. This module replaces them with a configuration screen.

  • Access profiles — a reusable set of restrictions shared by several users.
  • Per-user restrictions — the same families, configured directly on the user form.
  • Both sources are merged with a “most restrictive wins” rule: nothing ever re-authorises what another rule forbids.

The Hide Chatter Everywhere checkbox, on the profile as well as on the user, hides the chatter on every model at once.

Design principles

  1. Two layers, always. The interface is cleaned up for comfort (view create / edit / delete / duplicate / export_xlsx attributes, attributes injected on fields), and the ORM raises an AccessError (check_access, write, copy, export_data). Hiding a button is not security: only the second layer blocks a direct RPC call.
  2. One cached resolver. cpss.access.resolver._get_restrictions is decorated with tools.ormcache('uid'): every view load and every access check is a dictionary lookup. Any write on a profile, a rule or a user calls registry.clear_cache(), so a change is live on the next request, without restarting.
  3. A database with no rule pays nothing. Before that resolution, _has_any_restriction() answers in a single query, cached for the whole registry.
  4. Lockout-proof. The superuser, administrators (base.group_erp_manager) and members of the Access Manager group are never restricted, whatever the configuration. Nobody can lock themselves out.
  5. Filtering outside the native caches. ir.ui.menu.load_menus, _visible_menu_ids and ir.actions.actions.get_bindings are cached by Odoo on the user's set of groups. The module therefore filters around those methods, never inside them — otherwise two users sharing the same groups would share the same menus.

Two choices worth explaining

Buttons are blocked server side

A Button rule carries the name of the button, that is the method it calls — exactly what the web client posts to /web/dataset/call_button. The controller is overridden to refuse the call: hiding the button and blocking the method are the same rule. Notebook pages and links have no server-side counterpart: they are containers, and what they contain is protected by the field and model rules.

Domains do not go through ir.rule records

In Odoo, record rules coming from different groups are combined with OR: adding a rule through a technical group would widen what the user sees, the exact opposite of the goal. The module overrides ir.rule._compute_domain (cached per user) and combines its domain with AND on top of the native result. It is the only way to express “on top of everything else, this user sees less”.

Installation

Standard installation, no external Python dependency and no configuration file to touch.

odoo-bin -d mydb -i cpss_access_management

Dependencies: base, web. The module has no demo data, so it behaves identically on a demo database and on a production one.

Configuration

  1. Give the functional administrator the Access Manager group (Settings > Users & Companies > Users).
  2. Open Access Management > Access Profiles and create a profile, for instance Limited Salesperson.
  3. Fill in the tabs you need (Menus, Models, Fields, Buttons & Tabs, Reports, Domains), then assign the users in the Users tab.
  4. For a one-off restriction, use the Access Management tab directly on the user form instead of creating a profile.
  5. Log in as the restricted user to check the result — a change is effective on the next request, no restart needed.

Things to know

  • A readonly field is also blocked on write server side: a restricted user cannot bypass the attribute with an RPC call. Same for invisible.
  • A field cannot be required and invisible for the same target: a constraint forbids it, otherwise the record could never be saved.
  • View nodes are altered in get_view() and never in _get_view(), whose result is shared between users by the view cache.
  • The module inherits base, therefore every model: each entry point starts with a cache read and returns immediately when the user carries no restriction, which is the case for the vast majority of requests.

Known issues / Roadmap

Hiding the Add Custom Filter button (and its group-by counterpart) has no server-side extension point: it would require a JavaScript patch of the search component. This is deliberately not done — a patch that cannot be tested in depth on that component would break the search bar for every model.

The predefined filters and group-bys of a model are removed from the arch server side, and the domain rules remain the real protection: a custom filter never reveals a record excluded by a domain.

Automated tests

The automated test suite lives in the tests/ folder. It is never loaded in production: Odoo only imports that package when the server runs with --test-enable or --test-tags, and the tests are neither listed in the manifest nor imported by the module. There is nothing to remove before going live.

  • test_access_management.py — per-user resolution, profile / user merge, menus, models, fields, and enforcement on both layers.
  • test_access_advanced.py — buttons through the real /web/dataset/call_button route, notebook pages, chatter, filters, reports and record domains.
